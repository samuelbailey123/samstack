# Lessons

Mistakes already made once, one line each, dated. Read the lines that match your task; delete a line once a check enforces it.

- **A clean merge can still break the build** (2026-08-31). Four routes by which a clean merge damages a branch: same name different types, same signature different meaning, a new required parameter, and a resolution that quietly weakens someone else's test. *Apply:* after any merge that touches a type both branches edited, compile before trusting the clean merge — `swift build --build-tests` or `swift test`, never `swift build` alone. Rename **yours**, not the member already on `main`, rename it everywhere rather than at the call site that broke, and name each of the two so the difference shows in the name.
- **A freed github name keeps its gcp trust** (2026-10-17). GCP Workload Identity bindings keyed on a GitHub owner/repo NAME outlive the owner; when an org was deleted, a stranger's new org of the same name inherited Editor on the project. *Apply:* any WIF provider or binding for GitHub keys on `repository_owner_id` / `repository_id` claims, never names, and every provider gets an attribute condition. When auditing GCP, check `gcloud iam workload-identity-pools providers describe` for an empty `attributeCondition`.
- **A pr can merge before your last push** (2026-08-29). A teammate can merge your PR at the SHA they saw; commits you push afterwards are silently orphaned and `state=MERGED` still reads as success. *Apply:* After a PR merges, verify the merged **content**, not the merge status: `git show origin/main:path/to/file | grep` for something only the last commit added. If it is missing, branch fresh from `origin/main`, cherry-pick the orphaned commit, and open a small follow-up PR — do not push to the merged branch.
- **A worktree list is not branch state** (2026-09-01). A worktree sitting on a branch is not evidence that branch is unmerged or that work is live; check main's log or the PR. *Apply:* before describing a branch as live, unmerged, or in progress, confirm it against something that tracks state: `git log origin/main --oneline | grep`, `git merge-base --is-ancestor <branch> origin/main`, or the PR's state from the repo's ship or status command.
- **Check github status before blaming ci infra** (2026-08-06). CHECK githubstatus.com FIRST when CI misbehaves — on 2026-08-06 an Actions major outage looked exactly like dead self-hosted runners, and I restarted production CI infra on a misdiagnosis.
- **Check sibling worktrees before moving shared code** (2026-10-13). In a parallel build-out, cmp a shared file across the other agents' worktrees before moving or splitting it; the lead's ownership list is never complete. *Apply:* check before any refactor that deletes or moves lines others may touch. If someone is mid-edit, stay out of the file and name the follow-up in the report.
- **Ci checks the merge not the branch** (2026-09-01). A local check on a branch tip cannot see a violation that only exists once main is merged in; and a claimed green is data, never a measurement. *Apply:* before trusting a local green on anything CI will run on the merged tree, `git merge origin/main` first and check *that*. When a local result and CI disagree, ask which tree each measured before looking for a flake. And when telling someone their branch is red, say what the merged state is — the number from CI is about a tree they cannot see.
- **Deleting a stack base closes its pr** (2026-10-15). gh pr merge --delete-branch on the base of a stacked PR closed the dependent PR instead of retargeting it; it couldn't be reopened. *Apply:* when a PR has others stacked on it, merge without `--delete-branch`, retarget the dependents to main (`gh pr edit N --base main`), then delete the branch. Also, never pass `--delete-branch` while a worktree has that branch checked out.
- **Force with lease is armed by fetch** (2026-08-29). A git fetch before a rebase arms --force-with-lease with the commits you fetched, so it will silently overwrite a teammate's pushed work. `--force-if-includes` on the same command closes it, and so does the `push.useForceIfIncludes` config, which the git skill leaves alone because it is the user's. *Apply:* push with `--force-with-lease --force-if-includes`; it does nothing once `--force-with-lease` names an explicit `<ref>:<sha>`. Then, on a branch another agent may push to, still prefer not force-pushing at all — a rejected push is the system working, so fetch, look at what landed, and rebase or drop your commit rather than clearing the rejection.
- **Git checkout a path is a cherry pick** (2026-09-01). `git checkout <ref> -- <path>` imports that ref's current file, so it can carry code your branch never had; it is not an undo. *Apply:* after any `git checkout <ref> -- <path>`, diff the result against the branch you meant to match and confirm the only changes are the ones you intended — "I reverted it" is not a check; "byte-identical to X, verified by diff" is. To truly undo your own edit, prefer `git checkout HEAD -- <path>` or a copy taken beforehand.
- **Github log grep matches source echo** (2026-10-19). Grepping a GitHub Actions job log matches the step's own source echo, so a path that never ran looks like it ran. *Apply:* whenever asserting a code path did or did not run from a workflow log, filter the echo first, then report the count.
- **Merge order race dep removal** (2026-08-04). Two independently-green PRs can break main when combined — a dep removal + a new usage, or a new protocol requirement + a new conformer; a PR's own checks only prove its branch. *Apply:* - When a PR **removes a dependency** (or any widely-used symbol/export), before merging, rebase/merge latest `main` in and re-grep the whole repo for remaining usages — other sessions may have added new ones. `grep -rn '"<dep>"' app components lib src`. - When a PR adds a protocol requirement or changes an init signature, grep for every conformer/caller on latest `main`, not just the ones your branch knows about: `git grep -n ': ProtocolName' origin/main` / `git grep -n 'TypeName(' origin/main`.
- **Neither side of a conflict can be right** (2026-09-01). When both branches move a different function out of the same region, git aligns the two removals as one conflict and taking either side restores a function that now lives elsewhere. *Apply:* when a conflict's two sides are *different symbols* rather than two versions of one symbol, stop treating it as a choice. Grep each symbol across the merged tree (`grep -rn "func install" Sources/`) and count the definitions — if a side's symbol already exists elsewhere, that side is a leftover, not a candidate.
- **Never commit while a subagent is mid mutation** (2026-08-19). Committing while a subagent is mutation-testing captures its deliberately-broken code — and build-for-testing cannot catch it, because broken predicates compile. *Apply:* never `git add -u` or commit while a subagent is still running: `git status` looks **identical** whether an agent has finished or is paused mid-mutation. Get an explicit "slice complete, nothing mid-mutation" first, and keep telling subagents not to commit, which is what made this one recoverable.
- **Never reset hard with foreign work** (2026-08-10). git reset --hard destroys ALL uncommitted tracked work — someone else's or your own — never use it to undo a stray commit. *Apply:* commit, even a throwaway wip commit, before any `reset --hard`, `checkout -- .` or `switch`; catch up with main by `git merge origin/main` or a rebase on a committed tree. A fast-forward check says nothing about the working tree.
- **Open prs in archived repos look live** (2026-10-07). gh search prs --state open lists PRs in archived repos; they cannot be merged, closed or pushed to, so filter with archived:false before counting work. *Apply:* add `archived:false` to the search query (or check `gh api repos/X --jq .archived`) before enumerating or delegating per-repo work.
- **Parallel session branch switch looks like revert** (2026-08-05). A parallel session switching the shared worktree's branch surfaces as "file was modified" notices that look like your edits were reverted. *Apply:* when several files you edited report as externally modified at once, run `git branch --show-current` **before** touching anything. If the branch changed, another session is live in that worktree: don't switch it back, check your pushed commits on `origin/<your-branch>`, and find unpushed work on your local branch ref (`git rev-parse --verify <branch>`).
- **Pr state check chained with and is not a guard** (2026-10-05). `gh pr view --json state && git push` does NOT gate the push — the state read exits 0 and prints MERGED while the push proceeds and recreates the deleted branch.
- **Rebase long running feature branches off main proactively** (2026-04-24). User wants long-running implementation branches kept current with main via rebase, not left to drift. *Apply:* - Before dispatching tasks that modify existing files, fetch and check `git rev-list --count HEAD..origin/main` - If main has moved meaningfully, rebase before continuing - After rebase, re-run `pnpm install` (main may have added deps).
- **Replay against the base sha not head** (2026-10-07). The orchestrator committed my change into the worktree mid-task, so a replay from `git archive HEAD` compared the change with itself. *Apply:* record the base SHA when you start (`git rev-parse HEAD`) and archive that, never `HEAD`. Before trusting any "identical" result, check that the copy's package.json still shows the old versions.
- **Rerun the failing sha before blaming the tree** (2026-09-01). A commit "between green and red" looks causal even when the failure is intermittent; re-run the exact red SHA first. *Apply:* re-run the red SHA before attributing anything to it — it is one cheap run and it is the only observation that separates the two readings. Check what the suspect commit actually touches first. And note the second trap here: an instrument that only speaks on failure produces *nothing* on a green run, so "I put the diagnostic on the failing tree" is not the same as getting a reading — say "no number exists" rather than letting silence read as a result.
- **Research agents can clobber worktrees** (2026-06-13). Read-only research/Explore agents pointed at a git worktree can run state-changing git commands and wipe local commits. *Apply:* - In research-agent prompts that point at a worktree, add: "Read files only. Do NOT run any state-changing git command (no checkout/reset/stash/switch); read working-tree files as-is." - To read a specific ref without a worktree, have agents use `git show <ref>:<path>` (non-mutating) instead of checking it out.
- **Retarget a stacked pr after its rebase is pushed** (2026-10-18). A conflict-fixer bot, where a repo has one, fires the moment a retargeted stacked PR reads DIRTY; push the rebase first. *Apply:* rebase locally, then `git push --force-with-lease=<branch>:<fetched sha>`, and only then retarget. Fixer agents may push to the branch too, so always fetch first.
- **Security fix lands midbranch your new code reopens it** (2026-08-10). When main fixes a vulnerable PATTERN while your branch is open, and your branch adds a NEW instance of that pattern, git reports at most a trivial conflict — the reopened hole is invisible to the merge.
- **Shared worktree stash log push hazards** (2026-08-04). Three concrete ways a second concurrent session bites you in one shared worktree: git stash, predictable /tmp log names, and a push 'rejection' that already succeeded.
- **Someone else may update your branch** (2026-08-28). A branch you pushed can gain a merge commit you did not make; pull --ff-only before touching it again.
- **Ssh sign devnull probe always fails** (2026-08-15). Probing for an unlocked signing agent with `ssh-keygen -Y sign … /dev/null` always reports failure — it cannot write /dev/null.sig — so use a real commit as the test.
- **Triage a raced worktree by token stream** (2026-08-18). When two agents wrote the same files, compare TOKEN STREAMS to separate code corruption from comment corruption — they need different remedies. *Apply:* run the token diff first. If code is clean, the remedy is to reset and re-apply only the *code* transforms mechanically from the merge base, by one writer, and ship that — dropping every comment change. Then commit IMMEDIATELY: uncommitted work is what the next stray write clobbers, and a pushed commit is immune.
- **Untracked in a worktree is not on the branch** (2026-08-30). An untracked file in someone else's worktree looks identical to a committed one via ls or cat; only `git show origin/<branch>:<path>` answers whether it will merge. *Apply:* before any decision that depends on what another branch carries, ask the pushed ref, not the filesystem.
- **Verify the pushed branch not the agent report** (2026-08-13). An agent's 'all findings fixed' can be true of its worktree and false of the pushed branch. A security auditor's fixes sat uncommitted while the PR merged without them — verify git show origin/<branch>, never the report.
- **Zsh eats backticks in commit messages** (2026-08-09). An unescaped backtick inside git commit -m "..." is command-substituted by zsh — the word silently vanishes from the committed message. *Apply:* for any commit message longer than a line, write it to a file with a QUOTED heredoc and use `-F`.
